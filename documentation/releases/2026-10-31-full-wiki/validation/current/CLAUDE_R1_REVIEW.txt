# Findings

## F1 · SEV-HIGH — the separately attached HTML is a browser DOM snapshot, not the build

`Missy_offline_2.html` is **28,081,339 bytes**, SHA-256 `ef45631c…03fa08` — 159 bytes larger than
the frozen build and a different hash. It is not a variant build; it is a **saved page**:

| Marker | Packaged build | Attached file |
|---|---:|---:|
| `<script src="chrome-extension://ofaokhiedipichpaobibbnahnkdoiiah/…/frames_handler.js">` | 0 | **1** |
| `<style id="plotly.js-style-global">` (injected at runtime by Plotly) | 0 | **1** |
| `<head>` (the build has no `<html>`/`<head>`) | 0 | **1** |
| `data-boot-step="1" class="is-loaded"` (runtime state) | — | present |

Attributes are serializer-normalised (`disabled=""`, `<path/>` → `<path></path>`), a runtime
`title=` is added, and `<html class="missy-starting">` is the boot class.

**Consequence:** reviewing it would have measured a page that had already run, plus a third-party
extension. It also contains executable script from that extension, which is not part of your
product and whose behaviour you do not control.

**Checked for disclosure:** 96,638 characters of visible text, **no `SC_` identifiers in rendered
text**; the one `SC_` match is inside embedded script, and the nine `DEMO_SAMPLE` hits are
synthetic. No laboratory identifier leaked. But a DOM snapshot of a *loaded* session could, so this
should not become a habit for sending builds.

**Action:** discard it for review purposes. Send `dist/Missy-public.html` with its hash.

## F2 · SEV-HIGH — my earlier "zero embedded audio" statement is withdrawn; here is the measurement

You are right, and the correction is larger than the wording suggests:

- **221** `data:audio/mpeg;base64` URIs
- **10,858,704 bytes** decoded (10.36 MiB)
- **14,478,272 characters** of base64 in the file
- → **51.6 % of the 28 MB build is embedded speech**

Every clip: **22,050 Hz mono, 48 kbps, ~4.3 s**, encoder `Lavf61.7.100` / `Lavc61.19` / `LAME3.100`
(FFmpeg). Largest single clip 481,089 bytes.

**The licensing point the bytes can and cannot settle.** All 221 carry a `TSSE` encoder frame and
**nothing else** — no `TIT2`, `TPE1`, `TENC` or `COMM`. The containers establish *how* they were
encoded and are silent on *what produced the voice*. A re-encode through FFmpeg erases source
metadata, so **provenance cannot be recovered from the artefact** and must be documented at
creation time.

`wiki/VoiceAndAudio.md` already says *"Per-asset audio licensing must be reviewed separately from
the source-code licence."* That is correct but not sufficient for a 10 MiB redistributed asset set.
See correction C1.

## F3 · SEV-MEDIUM — `unchanged_ast` (3,440) exceeds `baselineFunctions` (3,423) by 17

In `INDEX_SUMMARY.json` and `VALIDATION_SUMMARY.json`. The rest of the arithmetic is sound and I
verified it:

- first-party partition `1724 + 756 + 187 + 3440 + 73 = 6180` = `firstPartyFunctions` ✓
- `6180 + 5552 = 11732` = `totalFunctions` ✓

But a baseline of 3,423 functions cannot contain 3,440 unchanged ones. The only consistent reading
is that `unchanged_ast` counts **current functions whose canonical AST matches some baseline AST**,
with at least 17 current functions sharing an AST with an already-matched baseline function —
duplicate bodies, which is normal. The *label* is wrong, not the number. A reader will read
3,440 / 3,423 as impossible and distrust the whole index.

## F7 · SEV-MEDIUM — the MARA preset test is stale, and the fix is not to restore the preset

# Answers to the eight questions

**1 · Separation of historical, current, coverage and scientific validation — mostly yes.**
`WORKFLOW.md` step 8 (*"Do not rewrite old results as current results"*) and the crosswalk's
repeated "preserve as historical" are the right structure. `VALIDATION_SUMMARY.json` keeps
`scope: "Function entry is execution evidence, not an individual correctness proof."` — exactly the
distinction that matters. **Weakness:** `CLEAN_CONFIRMATION.md` leads with "22/24 passing suites",
a number that averages a product result with two infrastructure failures. See C2.

**2 · The function inventory distinguishes the three categories correctly.** `firstParty`
true/false splits 6,180 / 5,552 cleanly; `form` separates `anonymous` 4,107 from `declared` 2,073;
`comparison` keeps `ambiguous_name_match` (187) as its own class rather than folding it into
matched or changed. The note *"Unique-name matches are candidates, not proof of semantic identity"*
is the correct caveat and is stated in both summaries. The one defect is F3's label.

**3 · Instrumentation is entry-counting only, and the clean rerun is the right control** —
"Function entry only in a separate review artifact; no production file modified", and the HTML hash
is unchanged after the clean run. The five harness diffs are all harness-side: four add a
`chime(){}` stub or re-point a `require` path; the fifth is the PCRD cancel flag. **None alters
application semantics.**
**Checks still needing clean, uninstrumented confirmation:** the PCRD reader family (F4), the whole
archive-intake path (F6), and anything whose verdict depends on a probe reading internal state
rather than observable output. Also worth one explicit run: the four suites whose harness gained a
`chime(){}` stub, confirming the stub is not masking a missing call the production code expects.

**4 · Next targeted tests.** 2,492 first-party functions unobserved (847 declared, 1,645
anonymous). Filtering to declared, reader/result-relevant, non-cosmetic gives **136**. Priority:

1. **`readZip`** — ambiguous match *and* unobserved *and* the archive entry point (F5).
2. **The PCRD family** — 14 functions, all unobserved, including `pcrdDecryptContainer` and
   `pcrdCRC`. Needs a lawful fixture or a declared boundary-only test.
3. **`integrityEvents`**, **`mgViewExport`**, **`selApplyCsv`**, **`selCsvTemplate`**,
   **`selReadme`** — all `changed_same_unique_name`: the body changed under an unchanged name, so
   the index cannot vouch for them and nothing executes them.
4. **`exportRecord`**, **`maraExportSample`**, **`maraWellID`**, **`csvRows`** — export-path
   integrity, `new_named`, unobserved.

Deprioritise the 12 cosmetic unobserved (tooltip/animation/badge).

**5 · Yes, stale.** See F7 for the current oracle.

**6 · Synthetic ZIP fixture.** Generate deterministically from a committed script: stored member,
deflated member, nested UTF-8 path, member exceeding the declared size limit, deliberate CRC
mismatch, and a path-traversal attempt. Assert the reader's *rejections* as firmly as its successes.
**Report its scope separately:** it exercises the container reader and the limit/CRC guards only. It
does **not** reproduce real vendor archive quirks — the mixed-endianness ICFF payloads, the variable
12/13-byte thermal headers, undeclared payload compression — and the documentation must list those
as still untested rather than let the new fixture's pass rate stand in for the missing legacy one.

**7 · Claims audit.**
*Voice support* — `wiki/VoiceAndAudio.md` is accurate and appropriately hedged ("depends on browser
capabilities", "headless emulation … does not prove recognition accuracy"). Good.
*Recorded English speech* — "221 recorded English phrases" is **exact**; I counted 221. The
different-units note (122 registry entries ≠ 221 phrases ≠ 515 catalogue entries) is well made. I
could not verify 515 from the HTML — no `SOUND_CATALOGUE`/`RECORDED_PHRASES` identifier is present
under those names, so the count is not independently checkable from the artefact; name the symbol.
*Audio licensing* — understated. See F2 and C1.
*Privacy* — `START_HERE.md` is right that download pseudonymisation ≠ speech pseudonymisation, and
right that headphones are irrelevant to the technical distinction. **But neither `Limitations.md`
nor `VoiceAndAudio.md` states it.** See C3.
*Intended use* — `Limitations.md` is strong. The sentinel paragraph and the "missing evidence must
not become an unsupported negative" sentence are the two best lines in the documentation set.

**8 · Crosswalk.** Structurally sound; the per-volume "current update obligation" phrasing avoids
restating old results as current, and volumes 9–11 and 14 correctly refuse to infer current
correctness from static atlases. Three omissions: no volume carries the **embedded-audio asset
register** (10.36 MiB, 221 files) — volume 17 is the natural home; volume 3 claims "narrow test
scope" without naming the **two suites with no current evidence**; volume 15 says "locked-file
cancellation is not decryption validation", which is right, but should add that the cancellation
path is **why** the PCRD functions are unobserved.
